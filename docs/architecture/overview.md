# MemForge Architecture Overview

Version: 1.0.0. Describes the package as built. The `gpg` and `keyless` commit-trust modes are specified and refused by the package until their proofs pass.

## 1. High-level architecture

MemForge is a file format and a set of command-line tools for the persistent memory of coding agents. A memory is a markdown file with YAML frontmatter in a memory folder. Agents and people write those files; the tools validate them, generate the `MEMORY.md` index, the recall index and an `AGENTS.md` surface from them, scan them for secrets, audit them, and commit them to git. MemForge has no server and holds no keys. Everything runs as the user on the user's machine, against folders the user owns. A folder that several people share is a git repository; `memforge sync` takes in new history from its remote only when every first-parent commit is signed by a signer the store's committed list names. The package's own code opens no network connection. The programs it starts that can reach a network are the `git fetch` that `memforge sync` runs against the user's configured remote, and an LLM dispatcher command the operator supplies to `memory-dedup`, `memory-lint` or `memforge-detect`.

The system has five planes:

- **Memory content**: the `.md` files in a memory folder, the rollup subfolders, `MEMORY.md`, and the `.memforge/` control files as they stand in the work tree. Anyone or anything that can write the folder can change them, so every tool treats them as untrusted input.
- **Tools**: the `memforge` dispatcher (`init-store`, `sync`, `paths`), the per-tool console scripts (`memory-audit`, `memory-index-gen`, `memory-recall`, `agents-md-gen`, `memory-dlp-scan`, `memory-watch` and the rest), and the Claude Code hooks under `adapters/claude-code/hooks/`. They run with the user's own permissions.
- **Store repository**: the git repository of a shared store: its history, the signer list committed under `.memforge/`, and the local state key `memforge.verifiedHead` in `.git/config`.
- **Remote**: the git remote the store's upstream setting names, its host, and the teammates who can push or merge there.
- **Release pipeline**: the project's GitHub repository, its `release.yml` workflow and the `pypi` environment, and the PyPI project `ildan-memforge` that users install from.

## 3. Key endpoints and trust roots

MemForge serves no network endpoint.

| Endpoint or root | Direction | Purpose |
|---|---|---|
| The remote named by `branch.<branch>.remote` | `memforge sync` to the git remote (`git fetch`) | Fetches only the branch named by `branch.<branch>.merge` |
| Operator-supplied dispatcher command | `memory-dedup`, `memory-lint`, `memforge-detect` to whatever the command reaches | Near-duplicate detection and lint suggestions; refused unless the command is a known local model runner or the operator passes the cloud opt-in |
| `gitsign` trust roots and transparency log | `gitsign` to its configured endpoints | `keyless` verification; the mode is refused, so no run reaches them |
| `https://pypi.org/project/ildan-memforge/` | User to PyPI (`pip install`); `release.yml` `publish` job to PyPI | Package download; upload by trusted publishing |
| GitHub REST API (`repos/<repo>/git/ref/tags/<tag>`, `repos/<repo>/git/tags/<sha>`) | `release.yml` to GitHub | Reads the release tag object, its target and its verification state |
| `https://github.com/jgm/pandoc/releases/download/<version>/` | `release.yml` `pdf` job and the CI `architecture-pdf` job to GitHub | Downloads the pinned pandoc, checked against the sha256 in `docs/pdf/toolchain.conf` |
| Chrome for Testing download, by `browser-actions/setup-chrome` | `release.yml` `pdf` job and the CI `architecture-pdf` job | Installs the pinned Chrome version; `build-pdf.sh` refuses any other version. The workflow pins the version, not a checksum |
| Sigstore and the GitHub attestations API, by `actions/attest-build-provenance` | `release.yml` `attest` job, with the run's OIDC identity | Signs and stores the build provenance attestation over the release files |
| Signer list in a commit's first parent (`.memforge/allowed_signers`) | Committed by a listed signer; read by `memforge sync` from the first parent of each commit it checks | Decides which keys may sign the next commit |
| First-sync pin (`--trust-head <commit>` or `--adopt-local`) | Given by the user on the first `memforge sync` | Starting point of verification; history up to it is vouched for, not checked |
| `memforge.verifiedHead` | Written by `memforge sync` to `.git/config`; read by the next run | Lower bound of verified history |
| Release tag signature | Made by the maintainer's signing key; verified by GitHub | Gates the build and publish in `release.yml` |
| PyPI trusted publisher binding | Configured on PyPI; verified against the GitHub Actions OIDC token | Authorizes the upload without a stored token |

## 4. Primary path

The primary path is `memforge sync`, run by a receiver at the top level of a shared store.

1. `memforge sync` (module `memforge.sync`) checks, before it runs any program, that `--memory-root` has a `.git` entry of its own: `root_not_toplevel` when a folder above it has one, else `not_a_repository` (SC-08).
2. It resolves `git`, `ssh-keygen`, `gpg` and `gitsign` from absolute `PATH` entries only, refuses with `tool_in_store` if one resolves inside the store (SC-06), and prints one `verifier <name>: path=... version=... sha256=...` line for each. It then asks git for the top level and refuses with `root_not_toplevel` when the root is not it (SC-08). Its git commands against the store run in the user's environment less the repository-local git variables, such as `GIT_DIR` and `GIT_INDEX_FILE` (SC-05).
3. It reads `memforge.verifiedHead`. Unset, it requires a pin (`--trust-head <commit>` or `--adopt-local`) and the pin is the start; set, a pin flag is refused (`pin_refused`) and the state key is the start.
4. It fetches only the branch the local upstream setting names (SC-09).
5. It makes the throwaway verifier directory and runs every later git command there with a cleared environment (SC-05).
6. It picks the target: the fetched head if the local branch is its ancestor, the local head if the fetched head is its ancestor, otherwise `diverged`. It never merges or rebases (SC-07).
7. It walks the first-parent chain from the target back to the start. A start not on the chain is `history_rewrite`; a missing commit in a shallow clone is `shallow_range` (SC-07).
8. For each commit, oldest first, it reads the one signer list in the commit's first parent, refuses a mode that is not released (SC-02), validates the list (SC-03), requires the commit's own tree to hold one valid list (SC-04), and checks the signature against the parent's list (SC-01). The first failure stops the run with exit 2, naming the commit and the reason.
9. Without `--check`, it fast-forwards the local branch with `git merge --ff-only`, then writes the target to `memforge.verifiedHead` (SC-08). With `--check`, it stops before the fast-forward and changes no local branch, work tree or state key.

Paths beside the primary one:

- **Claude Code auto-commit.** `memory-auto-commit.sh` runs after each `Write` or `Edit` on a file under a Claude Code memory folder that is a git repository. It keeps only the absolute `PATH` entries and runs each program it needs by the path found there, skipping one whose real path is under `~/.claude/projects` or `~/.claude/global-memory`; `readlink` must also be a regular file, or a link in `/usr/bin` or `/bin` whose target is outside the stores. It does nothing when `cat`, `jq`, `git`, `tr` or `readlink` is missing or skipped (SC-06). In the store it unsets the repository-local git variables (SC-05). It runs `memory-frontmatter-backfill --apply` and `memory-recall --rebuild` when they are found that way, then commits the written file and the `.md` files outside `.memforge/`, naming each to git with `:(literal)` (SC-10, SC-12, SC-13, SC-40). It never commits the recall index and never pushes.
- **`memory-watch`.** Commits the changed `.md` files outside `.memforge/` in each watched git repository after a debounce (SC-11), naming each to git with `:(literal)` (SC-40) and running git without the repository-local git variables (SC-05). It never commits the recall index and never pushes.
- **Write gate.** `gate-memory-frontmatter.py` denies a Claude Code `Write` or `Edit` whose resulting frontmatter does not parse or lacks `name`, `description` or `type` (SC-24). On an internal error it allows the write and prints one stderr line naming the error. `memory-validate` makes the same parse check from a git pre-commit hook.
- **Index and recall generation.** `memory-index-gen --write` builds `MEMORY.md` from frontmatter (SC-16, SC-17), and `--with-recall-index` or `memory-recall --rebuild` builds `.memforge/recall-index.json`. `memory-recall` compares a fingerprint of the memory files with the one in that index before every query and rebuilds the index on a mismatch or when a file changed within 2 seconds of the index's build time (SC-41), then prints matching descriptions, never bodies (SC-18, SC-19).
- **Recall hook.** `memory_recall_hook.py` runs on each Claude Code prompt and starts `memory-recall --stdin` by absolute path: the one in the scripts folder of the Python environment that runs the hook, else the first on an absolute `PATH` entry, refused inside a memory store and, for one from `PATH`, inside the working folder, the Claude Code and memforge home folders or the repository that holds any of them (SC-06). When none may be started it prints `memory_recall_hook: recall is off: <reason>` on stderr and lets the prompt through.
- **AGENTS.md generation.** `agents-md-gen` writes `AGENTS.md` into the repository `--cwd` names, from every folder `memforge paths` gives for that repository and from `<cwd>/CLAUDE.md`, and reads nothing else, no file in the home folder included. Memories are filtered by sensitivity, each name and description is cleaned to one line, each pinned body is copied as literal text inside a code fence, and the result is scanned for secrets before the write (SC-32, SC-33, SC-34, SC-37).
- **DLP scan.** `memory-dlp-scan` scans staged content, named files or the memory folders for secrets and for content above a file's declared sensitivity (SC-21).
- **Audit.** `memory-audit` checks the integrity invariants at HEAD and the commit-history rules over the last 30 days, merges included (SC-20, SC-22, SC-23). A memory folder it cannot list is an integrity violation, and the audit goes on to the next folder.
- **Link rewriting.** `memory-link-rewriter` (`check`, `rename`, `rename-batch`, `upgrade`) reads every file in the folder before it changes anything; a file or folder it cannot read, the memory folder itself included, stops the command with exit 2 and nothing is moved or written. `memory-rollup` runs its `rename-batch`; it refuses a source that is a link or not a regular file, a history folder that is a link or not a folder (in `create`, `undo` and `list`), and `undo` takes each path a history record names only where `create` writes it; `create` refuses before moving any file when an existing history folder cannot take the record (SC-14).
- **Resolve and promote.** `memforge-resolve` and `memory-promote` commit only the files they changed, with file names passed to git literally (SC-40). `memforge-resolve` opens the snooze folder one name at a time from the memory root and refuses, before it changes any member, a `.memforge` or `.memforge/snoozes` that is a link (SC-14).
- **Push.** No memforge tool pushes. The user pushes with git, and the host's rules decide what lands.
- **Release.** A maintainer pushes a signed tag; `release.yml` checks it, tests, builds and publishes (SC-27 to SC-30). It also builds the architecture PDF from the tagged sources, attests every file the GitHub Release attaches, and lists each file's sha256 in the release notes (SC-38). The PDF build refuses raw content in any format, images other than the diagrams, attributes and metadata in the docs and any input that is a link, writes the diagrams and stylesheet into a page that loads no file, and Chrome prints with no route to the network (SC-39). See `docs/runbooks/release.md`.

## 5. Trust boundary posture

- **Memory content.** Trusts nothing. Tools read store files without following links (SC-14), report a memory folder they cannot list or look at, instead of walking it as empty or taking it for absent (every tool that reads a store, `memory-recall` excepted, since recall is fail-open by spec: SC-43) and, on every supported Python, a path inside a folder they cannot search instead of stopping with a traceback, show control characters from store text as visible escapes in their output (SC-42), bound frontmatter size (SC-15), treat names, descriptions and topics as untrusted when they build `MEMORY.md` (SC-16), and label recall output as untrusted reference text (SC-18). A memory written by a trusted signer can still carry a prompt injection; nothing in MemForge checks content for intent.
- **Tools.** Trust the user who runs them and the package as installed. They do not trust the current folder, the store or the repository that holds it: each tool and hook finds the programs it starts only on absolute `PATH` entries (the recall hook first in its own Python environment) and refuses one inside the folder it works on, and the tools also refuse one elsewhere in that folder's git repository (SC-06). Git commands a tool runs against a named repository ignore the caller's repository-local git variables (SC-05), and the tools that commit or read history by file name pass names to git literally (SC-40). `memforge-detect` runs its helpers in isolated mode (SC-26). An operator-supplied dispatcher command is run through the shell as given. Only `memforge sync` checks signatures. No other tool reads `memforge.verifiedHead`, warns about unverified content, or refuses because of it.
- **Store repository.** Trusts history up to the first-sync pin without checking it, and the signer list in each commit's first parent for the commit after it. Does not trust repository-local git configuration during verification (SC-05). The state key lives in `.git/config` under the user's account and is not in the work tree.
- **Remote.** Trusted to run the signing policy its host advertises and to be run by people who are not the attacker. `memforge sync` does not trust what it fetches: fetched objects are used only after every commit in the range passes. Plain `git pull`, `git merge` and `git checkout` bypass that check entirely.
- **Release pipeline.** Trusts GitHub's tag signature verification, the `main` branch history, the pinned action versions and the PyPI trusted publisher binding. Does not trust a tag push alone: an unsigned, lightweight or off-`main` tag stops the run before the build (SC-27).

## 6. Security controls summary

| ID | Control | Applies to |
|---|---|---|
| SC-01 | `memforge sync` accepts a first-parent commit only when `git verify-commit` passes against the `allowed_signers` list in that commit's first parent; an unsigned commit is `unsigned` (decided before its own list is read), any other failure `ssh_not_verified` | Stores whose receivers run `memforge sync`, `ssh` mode |
| SC-02 | `memforge sync` refuses a commit whose first parent carries a `gpg` or `keyless` list with `mode_unreleased`, before any verification of it | All installs |
| SC-03 | `memforge sync` validates the signer list before any signature check, with the grammar in the spec's "List grammar": a list over 1 MiB (decided from the object type and size before it is read, SC-44), control characters other than tab, an entry in any mode that is not tab and printable ASCII, a quote outside `namespaces="..."`, `cert-authority`, `valid-after` and `valid-before` make it `list_invalid` | Stores whose receivers run `memforge sync` |
| SC-04 | `memforge sync` refuses a signed commit whose own tree does not hold exactly one valid list with at least one entry (`list_removed`) | Stores whose receivers run `memforge sync` |
| SC-05 | `memforge sync` runs verification in a throwaway config-free bare git directory with a cleared environment (`HOME`, `TMPDIR`, `PROGRAMDATA` set to private empty folders; `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` set to an empty file; `GIT_CONFIG_NOSYSTEM=1`) and pins `gpg.format` and the verifier program with `-c`. The shell hooks `memory-auto-commit.sh` and `memory-read-tracker.sh` keep only absolute `PATH` entries, skip any program whose real path is under `~/.claude/projects` or `~/.claude/global-memory`, and use the first `readlink` on those entries that is a regular file, or a link in `/usr/bin` or `/bin` whose target is outside the stores. `memory_recall_hook.py` starts the `memory-recall` in the scripts folder of the Python environment that runs it, else the first on an absolute `PATH` entry, by absolute path, and refuses it inside a memory store (one found on `PATH` also inside the working folder, `~/.claude/projects`, `~/.claude/global-memory` and `~/.memforge`, also while `MEMFORGE_MEMORY_PATH` is set, and inside the repository that holds any of those folders or a store); run by an interpreter that cannot import memforge it searches `PATH` itself and refuses exactly the same folders; with none it may start it prints `memory_recall_hook: recall is off: <reason>` on stderr | All installs; the hook part where the Claude Code hooks are registered |
| SC-07 | `memforge sync` refuses a divergent branch (`diverged`), a start not on the target's first-parent chain (`history_rewrite`) and a missing range in a shallow clone (`shallow_range`); it has no override flag | Stores whose receivers run `memforge sync` |
| SC-08 | `memforge sync` writes `memforge.verifiedHead` only after a successful fast-forward, and refuses a memory root that is not its repository's top level (`root_not_toplevel`); a root without its own `.git` entry is refused before any program runs | Stores whose receivers run `memforge sync` |
| SC-09 | `memforge sync` fetches only the branch named by the local `branch.<name>.merge` setting from the remote named by `branch.<name>.remote` | Stores whose receivers run `memforge sync` |
| SC-10 | `memory-auto-commit.sh` commits only the written file and `.md` files outside `.memforge/`; it never commits the recall index, a signer list, `config.yaml`, a snooze or a waiver | Installs that register the Claude Code hook |
| SC-11 | `memory-watch` commits only `.md` files outside `.memforge/`; it never commits the recall index or anything else under `.memforge/` | Folders watched by `memory-watch` |
| SC-12 | `memory-auto-commit.sh` replaces control characters in the tool and file names with `?` before they enter the commit message | Installs that register the Claude Code hook |
| SC-13 | `memory-auto-commit.sh` and `memory-read-tracker.sh` ignore a path with a `.` or `..` segment or an empty project folder name | Installs that register the Claude Code hooks |
| SC-14 | Tools read and write store files through `memforge.discovery`, which refuses a symlink, a non-regular file and (for writes) a file with a second hard link, decided on the opened descriptor; on Linux and macOS the open walks folder handles down from the memory folder. `memory-read-tracker.sh`, which writes `.last_used.json` outside `memforge.discovery`, does nothing when the ledger is a link or not a regular file, and creates a missing one only where no name exists. `memforge-resolve` checks and deletes a snooze relative to the snooze folder's handle, opened one name at a time from the memory root, and refuses a `.memforge`, `.memforge/snoozes` or snooze that is a link or of the wrong kind before it changes any member. `memory-rollup create` refuses a source that is a link or not a regular file, and its fallback move copies without following a link and never replaces a file; `undo` takes each path a history record names only where `create` writes it and refuses a linked rollup folder or moved file; `create`, `undo` and `list` refuse a rollup history folder that is a link or not a folder, before they read or move anything; `create` tests an existing history folder with a probe file it makes in one exclusive step under a random name, removes only that file, and reports one it cannot remove | All installs; the folder-handle walk (and resolve's snooze delete by handle) on Linux and macOS only; the ledger part where the read-tracker hook is registered |
| SC-15 | Frontmatter over 65536 bytes, 10000 YAML nodes or 64 levels of nesting is a finding for that one file, not a stop for the run | All installs |
| SC-16 | `memory-index-gen` turns control characters, U+2028 and U+2029 in a memory's name, description, topic and file name into spaces, and leaves out of `MEMORY.md` (exit 1) a memory whose value carries a generator marker, an unclosed HTML comment or a code fence. The competing-claims block quotes every value a YAML reader would not read back as the same text, so the block always parses | All installs |
| SC-17 | `memory-index-gen --viewer-tier` and `--viewer-teams` leave out memories whose `access` labels the viewer does not satisfy, and list a restricted competing-claim member by `uid` only | Runs that pass a viewer filter |
| SC-18 | `memory-recall` prints descriptions only, under a preamble that marks them as untrusted reference context; it drops `do_not_inject` memories and any `access` label other than `public`, `internal` or a held `team:` label | All installs |
| SC-19 | `memory-recall --sensitivity-max <level>` drops memories above the level; an unknown sensitivity counts as `privileged` | Runs that pass `--sensitivity-max` |
| SC-20 | `memory-audit --export-tier <level>` (or `audit.default_export_tier`) reports a BLOCKER for each file whose sensitivity exceeds the level; a `privileged` file blocks even when `enforce_sensitivity_export_gate` is false | Runs with an export tier set |
| SC-21 | `memory-dlp-scan` reports secret, credential and PII patterns, a `sensitivity_label_mismatch` BLOCKER when content implies a tier above the label, and `deep_scan_failed` (BLOCKER) when an installed `detect-secrets` fails or resolves inside a scanned memory folder (`--memory-folders`) or the current folder (`--staged`); each excerpt it prints has every match on that line replaced by `[REDACTED]` | All installs; the deep layer only where `detect-secrets` is installed |
| SC-22 | `memory-audit` Tier 2 checks commits of the last 30 days: resolve-commit scope, unprefixed `superseded` transitions, `superseded_by` and `decision_topic` changes, member deletion (a live member moved into `archive/` counts), and config, snooze, waiver and alias edits. The config and snooze gates cover every committed path the loader can open as them: case variants, committed links on the way, and the in-repository file a link names. Link chains are followed as the file system follows them, absolute targets under the repository top included; a config link chain that cannot be followed to a file inside the repository is a `config link` BLOCKER, and any committed link at `.memforge`, at `.memforge/snoozes`, on the way to it or under it is a `snooze folder link` BLOCKER. The commit log is read NUL-separated, so no character in a subject can end a record early, and file names reach git literally (SC-40). A merge is judged by what it changes on its first parent. A finding on a merge is left to the merged branch only when the merge takes the branch's file while the first parent still holds the merge base's, or keeps the branch's `status`, `superseded_by`, `decision_topic` and `topic_aliases` for a change the branch made, and every branch commit that touched the path is one this audit checked (inside the window); otherwise it is reported on the merge. Git runs without the caller's repository-local git variables (SC-05) | Stores that are git repositories, where `git` is found outside the store and its repository |
| SC-23 | `memory-audit` reads `.memforge/audit-waivers.yaml` only as committed at HEAD, warns when the work-tree copy differs, and never waives a finding on a commit that changes the waiver file | Stores that are git repositories |
| SC-24 | `gate-memory-frontmatter.py` denies a Claude Code `Write` or `Edit` whose resulting frontmatter does not parse as a YAML mapping or lacks `name`, `description` or `type`; on any internal error it allows the write and prints `gate-memory-frontmatter: internal error (<error class>); write allowed unchecked` to stderr | Installs that register the `PreToolUse` gate |
| SC-25 | `memory-dedup` and `memory-lint` refuse a dispatcher that is not a known local model runner unless the operator passes `--allow-cloud-dispatcher` or `--allow-cloud` | Runs that use a dispatcher |
| SC-26 | `memforge-detect` runs its helper modules with `python -I` and this process's absolute import path, so a module in the working folder is not imported | All installs |
| SC-27 | `release.yml` stops before the build unless the tag is annotated, carries a signature GitHub verifies, and points at a commit on `main` | Project releases |
| SC-28 | `release.yml` runs the test suite and checks that `__version__`, the installed metadata, the CHANGELOG heading and the tag agree before it builds | Project releases |

## 7. Isolation model

MemForge has no tenants. One user runs the tools on one machine against folders that user owns. Separation comes from four places:

- **Folders.** The per-project folder is named from the git root of the working folder (or the working folder outside a repository), with every character other than an ASCII letter or digit replaced by `-`, so two projects get two folders. `MEMFORGE_MEMORY_PATH` overrides the choice. The tools default to the folders `memforge paths` prints for the current folder; `agents-md-gen` reads every folder those rules give for the repository `--cwd` names, in order, and names on stderr a `MEMFORGE_MEMORY_PATH` folder that yields no memories.
- **Repositories.** A shared store is one git repository with one `memforge.verifiedHead`; `memforge sync` refuses a store that is a subfolder of a larger repository.
- **Sensitivity.** The `sensitivity` field (`public`, `internal`, `restricted`, `privileged`; absent means `internal`) decides what `agents-md-gen` writes (SC-32), what `memory-recall` prints under `--sensitivity-max` (SC-19), what `memory-audit --export-tier` blocks (SC-20) and what `memory-dedup` and `memory-lint` send to a cloud dispatcher (SC-36). `memory-index-gen` does not filter by sensitivity. The Claude Code recall hook runs `memory-recall --stdin` with no `--sensitivity-max`, so on that path no sensitivity ceiling applies.
- **Access.** The `access` field decides what `memory-index-gen --viewer-tier` and `--viewer-teams` put in `MEMORY.md` (SC-17) and what `memory-recall` prints (SC-18). `agents-md-gen` does not filter by access.

These labels are filters on output the user generates. They are not access control: anyone who can read the folder reads every file in it. The `isolation` diagram shows which label each output honors.

## 8. Who receives what data

| Party | Receives | Direction | Retains |
|---|---|---|---|
| The user's agents | `MEMORY.md`, `AGENTS.md`, recall output (descriptions only), and any file the agent reads | Memory folder to agent session | Per the agent's own product terms |
| The git remote and its host | Every committed file: memory content, `.memforge/` control files, signer list, commit signatures, author identities, times and messages | User's `git push` to the remote | Until the store's owner removes it; history keeps it after deletion |
| Teammates with read access to the remote | The same as the host | Remote to their clones | In their clones, indefinitely |
| The repository that holds a generated `AGENTS.md` | Descriptions of memories at or below `--max-sensitivity`, bodies of pinned `public` memories, and the text of that repository's own `CLAUDE.md`; nothing from the home folder | `agents-md-gen` to `<cwd>/AGENTS.md`, then wherever that repository is pushed | Per that repository's host |
| Operator-supplied LLM dispatcher | `memory-dedup`: file names, names and types, plus descriptions only with `--no-redact-descriptions`; `memory-lint`: name, tags and description of each weak memory, and its body only with `--allow-cloud-body`; `memforge-detect`: lessons text and the rule catalog, to a local dispatcher only | Tool to the dispatcher command on stdin | Per the dispatcher's provider; a local runner keeps nothing off the machine |
| PyPI | The sdist and wheel | `release.yml` to PyPI | Published files cannot be overwritten |
| GitHub | The tag, the sdist, wheel, SBOM and architecture PDF on the release page, their sha256 in the release notes, and the build provenance attestation | `release.yml` to GitHub | Per the repository's settings |
| Sigstore | The attestation's signing request: the digests of the attested files and the identity of the `attest` job's run | `actions/attest-build-provenance` to Sigstore | Per Sigstore's terms |

MemForge sends no telemetry, no usage data and no crash reports. Nothing leaves the machine except by `git push`, the `git fetch` in `memforge sync`, a dispatcher the operator names, or a file the user copies out. `.last_used.json`, `.memforge-rollup-history/`, `~/.claude/memforge-hygiene-queue.json` and the throwaway verifier directory stay on the machine unless the user commits or copies them.

## 9. Key management

MemForge generates, stores, rotates and revokes no key.

| Key | Custody | Rotation |
|---|---|---|
| A signer's commit signing key (`ssh`) | The signer's machine or the organization's key service; the public half is a line in `.memforge/allowed_signers` | A listed signer commits a list change; removing a key stops later commits only |
| A signer's OpenPGP key (`gpg`, refused) | The signer's keyring; the fingerprint in `.memforge/allowed_gpg_fingerprints`; the public key in each receiver's keyring | As for `ssh`, plus the receiver's keyring |
| A `gitsign` identity (`keyless`, refused) | The organization's identity provider and Sigstore trust roots; identity and issuer in `.memforge/allowed_identities` | Short-lived certificates per signing |
| The maintainer's release tag signing key | The maintainer; GitHub holds the public half to verify tags | Outside the package; GitHub must still verify the tag |
| PyPI upload credential | None stored: a short-lived OIDC token issued to the `publish` job | Per run |
| Release attestation signing key | None stored: a short-lived Sigstore certificate issued to the `attest` job for its OIDC identity | Per run |

`memforge init-store --mode ssh` reads only the public half of the key named by `user.signingkey`. It never reads a private key file.

## 10. Telemetry

None. The tools write to stdout and stderr only. `memforge sync` prints the resolved verifier executables with their versions and SHA-256, one `mode` line per mode that judged a commit, and the verdict. Local records that some tools keep, all inside the user's folders and kept until the user deletes them: `.last_used.json` (read-tracker hook), `.memforge-audit-log.jsonl` (written only by `memory-audit-log append`, with an `operator` field defaulting to `$USER@hostname`), `.memforge-rollup-history/` (`memory-rollup` undo ledger) and `~/.claude/memforge-hygiene-queue.json` (`memforge-detect`).

## 11. Data handling

- **What moves.** Memory files move between the user's folders and git; commits move between the store and its remote by the user's `git push` and by `memforge sync`. Generated files (`MEMORY.md`, `AGENTS.md`) are derived from frontmatter and committed by the user or the hooks. The recall index `.memforge/recall-index.json` is derived too, but it is a local cache: no tool commits it, and `memory-recall` rebuilds it unless its fingerprint matches the memory files.
- **Who sees it.** The user, the user's agents, the git host, and everyone with read access to the remote or to a repository that holds a generated `AGENTS.md`.
- **What is never stored.** Private keys. Secrets are not meant to be stored: `memory-dlp-scan` reports them, and `agents-md-gen` refuses to write one. A memory file is plain text and MemForge is not a secrets store.
- **At rest.** Plain text on the user's file system and in git. MemForge adds no encryption and sets no file permissions beyond what `copy_file_inside` copies. Disk encryption, file permissions and the host's access rules are the user's and the host's controls.
- **Durability.** Git history is the only copy MemForge relies on. The remote and every clone hold the history; `memory-rollup` keeps an undo ledger. A local clone lost before a push loses its unpushed commits. MemForge has no backup or restore command.

## 12. Customer-side verification

Run these in a scratch store with `HOME` set to a scratch folder. Each was run against this release.

1. The tools search the folders you expect: `memforge paths` prints one folder per line and exits 0.
2. A first sync needs a pin: `memforge sync` in a store with no `memforge.verifiedHead` prints `memforge sync: no_pin: first sync needs --trust-head <commit> or --adopt-local` and exits 1.
3. The verifier is the one printed: every `memforge sync` run prints `verifier git: path=<absolute path> version=<version> sha256=<hex>` and the same for `ssh-keygen`, `gpg` and `gitsign` (`not found` when absent).
4. An unlisted key is refused: push a commit signed by a key that is not in `.memforge/allowed_signers`, then `memforge sync` prints `memforge sync: refused (ssh_not_verified): commit <id>: ... No principal matched.` and exits 2; `git log` shows the local branch unmoved.
5. An unsigned commit is refused: `memforge sync --check` over an unsigned commit prints `refused (unsigned): commit <id>: commit has no signature header` and exits 2.
6. `--check` changes nothing local: `memforge sync --check` ends with `check only: no local branch, work tree or verifiedHead was changed`, and `git config --local --get memforge.verifiedHead` prints the same id before and after.
7. A subfolder store is refused: `memforge sync --memory-root <subfolder>` prints `root_not_toplevel` and exits 1.
8. The auto-commit hook leaves the signer list alone: change `.memforge/allowed_signers` and a memory file, feed the hook a `Write` payload for the memory file, and `git log --stat -1` lists the memory file and not `.memforge/allowed_signers` or `.memforge/recall-index.json`, while `git status --short` still lists `.memforge/allowed_signers` as modified.
9. The export gate blocks: `memory-audit --path <folder> --export-tier internal --strict` on a folder with a `restricted` file lists it under the export tier and exits 1.
10. The viewer filter applies to `MEMORY.md`: `memory-index-gen --path <folder> --print --viewer-tier internal` leaves out a memory whose `access` is `counsel` or `privileged`.
