# MemForge Threat Model

Version: 1.0.0. Read with `overview.md`; control IDs (SC-nn) are defined in its section 6. Method: STRIDE per asset, against the system as built.

The table ranks nothing. Residual risk says what still works for an attacker and who owns the remaining control. Where a residual is one of the known limits stated in `CHANGELOG.md` (1.0.0, Security) or `spec/known-limitations.md`, it is quoted in those words.

## Assets

| ID | Asset | Where it lives |
|---|---|---|
| A1 | Memory content: memory files, rollup READMEs, `MEMORY.md` | The memory folders on the user's machine; the store's git history and its remote |
| A2 | The signer list (`.memforge/allowed_signers`, `allowed_gpg_fingerprints`, `allowed_identities`) | Committed in the store repository; read by `memforge sync` from each commit's first parent |
| A3 | The shared branch's history | The git remote and every clone |
| A4 | The local verification state `memforge.verifiedHead` and the first-sync pin | `.git/config` of the receiver's clone; the pin is a statement the receiver makes |
| A5 | Generated surfaces: `MEMORY.md`, `.memforge/recall-index.json` (a local cache), `AGENTS.md`, recall output | The memory folders; `<cwd>/AGENTS.md` in a project repository; the agent's context |
| A6 | Store control files: `.memforge/config.yaml`, `.memforge/audit-waivers.yaml`, `.memforge/snoozes/<topic>.yaml` | The store's work tree and history |
| A7 | Signers' private signing keys | The signers' machines or key services; never in MemForge |
| A8 | The user's files outside the memory folders | The user's file system, reachable by any tool that follows a link |
| A9 | The published package and the release tag | PyPI project `ildan-memforge`; the GitHub repository's tags and releases |
| A10 | Availability of the tools | The user's machine |
| A11 | The audit log `.memforge-audit-log.jsonl` | A memory folder, when the operator keeps one |
| A12 | Content classified `restricted` or `privileged` | Memory files carrying that `sensitivity` |

## Threats

| # | Asset | STRIDE | Threat | Existing controls | Residual risk |
|---|---|---|---|---|---|
| T1 | A1, A3 | Spoofing | Someone with no listed signer pushes a first-parent commit to the shared branch | SC-01, SC-03, SC-05, SC-09 | Stopped only for receivers who run `memforge sync`. "Unverified content reaches agents by any path other than `memforge sync`. Plain `git pull`, `git merge` or `git checkout`, edits or new files in the work tree, and never running `sync` all put unverified content in front of an agent. No other MemForge command checks verified state, warns or refuses. The control for that path is the git host's branch protection and required signed commits." Owner: the store's owner and the git host |
| T2 | A2 | Elevation of privilege | A commit adds its own signer to the list to authorize itself | SC-01 (the list is read from the first parent), SC-04 | "A listed key is trusted completely. There is no revocation, no reach-back and no second approval inside MemForge. Removing a key from the list stops later commits only. Any listed signer can add another signer." Owner: the store's signers and the host's review rules on `.memforge/` |
| T3 | A2 | Tampering | A process that can write one file in a listed signer's store gets a changed signer list committed under that signer's signature by an automatic commit | SC-10, SC-11 | A signer who commits by hand with `git add -A` can still commit a planted list change. The example watchers under `examples/scripts/` skip `.memforge/`; other watchers are the user's. Owner: the signer |
| T4 | A1 | Spoofing | A tool call's file name with a newline adds lines, such as a `Signed-off-by:` trailer, to a commit made under the user's signature | SC-12 | None identified for the hook's message; the hook replaces every control character. Messages written by other tools or by hand are the user's |
| T5 | A3 | Tampering | The remote rewrites history the receiver already verified | SC-07 | "A refused commit blocks everyone. Until the remote's owner removes it, every receiver who runs `sync` is refused. There is no override flag." Owner: the remote's owner |
| T6 | A3 | Tampering | A shallow clone hides commits in the range so they are not checked | SC-07 | The CHANGELOG carries one item open: "The shallow-range refusal depends on a parent object being absent rather than on the shallow file." Owner: the project |
| T7 | A4 | Tampering | Someone moves `memforge.verifiedHead` forward or pins past a refused commit | SC-08 (only a successful run writes the key) | "A pin vouches for history it does not check. A pin from a compromised teammate pins a compromised history. A local user can clone again and pin past a refused commit, or edit local configuration. MemForge offers no command for it and cannot prevent it." "The first-sync pin is a statement, not a check." Owner: the receiver |
| T8 | A3, A6 | Tampering | Repository-local, global or system git configuration (for example `gpg.ssh.revocationFile`) flips a verdict, or a repository-local git variable (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`) set by a git hook or a shell points a tool at another repository's history, waivers or index | SC-05 | "Environment injection through `GIT_CONFIG_COUNT` was not tested. The cleared environment used for verification is the mechanism that is relied on." Outside the verifier, tools drop only the repository-local variables; global and system git configuration still apply to them. `memory-dlp-scan --staged` keeps the inherited git environment, since it runs as a pre-commit hook where git sets `GIT_INDEX_FILE`. Owner: the project |
| T9 | A3, A8 | Elevation of privilege | A `git.bat`, `gpg.cmd`, `detect-secrets` or similar committed to the store runs in place of the real tool | SC-06, SC-08 | Still found by name: an operator-supplied dispatcher command, which runs through the shell as given, and the programs git itself starts, such as `gpg` or `ssh-keygen` for a signed commit. The example watchers run `git`, `python3` and `fswatch` by name. A program in the scripts folder of the Python environment memforge runs from is not refused for lying in the repository, only for lying in the folder the tool works on. `memory-dlp-scan --paths` does no folder check. On a system where every `readlink` on `PATH` is a link (busybox), the Claude Code hooks do nothing. `memory_recall_hook.py` refuses a `memory-recall` found on `PATH` inside a memory store, the working folder, `~/.claude/projects`, `~/.claude/global-memory` or `~/.memforge` (also while `MEMFORGE_MEMORY_PATH` is set), and inside the repository that holds any of them (found by walking up to a `.git` entry), and the one in its own Python environment only inside a store; when Claude Code is opened in a folder that holds the `PATH` program (a home folder kept as a git repository with `~/.local/bin` inside it, for example), recall is off there and the hook says `recall is off: ...` on stderr. Without memforge importable it searches `PATH` in standard-library code and refuses exactly the same folders; it has no environment of its own to try first. The tools' Windows lookup was tested by simulation, not on a Windows host, and the recall hook's lookup was not run on Windows. Owner: the user's `PATH` |
| T10 | A3 | Repudiation | Two receivers disagree on whether a commit is verified | SC-01, SC-05; the run prints the verifier paths, versions and SHA-256 | "In `ssh` mode verdicts agree only across receivers whose `git` and `ssh-keygen` executables behave the same; versions and SHA-256 values are printed, not pinned." "`gpg` and `keyless` verdicts can differ between receivers." Owner: each receiver |
| T11 | A1, A3 | Repudiation | An agent's commit is taken as the person's own act, or attribution is lost | None | "Agents commit under a person's signature. An agent that runs in a listed person's session produces commits that carry that person's signature. Per-agent attribution is advisory only (`agent_session`, `on_behalf_of`). Attribution does not survive a squash merge or a copy." Owner: the signer |
| T12 | A3 | Spoofing | A host admin, a compromised host, or anyone the host lets merge puts content on the branch | SC-01 for receivers who run `sync` | "The host and the people who can merge are in the trust base. A compromised host, a host admin, or anyone the host lets merge can put content on the branch. Hosts enforce signed commits and registered keys, not membership in the committed list, so an unlisted but registered signer can reach the branch. `sync` then refuses it for everyone." "Host-generated commits are unverified." Owner: the git host and the store's owner |
| T13 | A5 | Tampering | A trusted signer writes a prompt injection into a memory | SC-18 (recall output is labelled untrusted) | "A trusted signer can write a prompt injection. Signing proves who committed, not that the content is safe." `MEMORY.md` and `AGENTS.md` carry no such label. Owner: the signers and the agent's own handling of context |
| T14 | A5 | Tampering | One memory's name, description, topic or file name forges a line, a generated header or a competing-claims block in `MEMORY.md`, or a `# Repo-specific` or `## Critical rules` section in `AGENTS.md`; a pinned body or the `_memforge.yaml` preamble hides the generated sections in a code or HTML block; a value makes the competing-claims block fail to parse | SC-16, SC-37 | None identified for the name and description: the value is refused or flattened to one line, U+2028 and U+2029 included. A pinned body and the preamble are copied as literal text inside a backtick fence longer than any backtick run in them, so no line of either can close the fence and nothing in either reaches the generated text; a body's headings and lists show as source text in a code block, not rendered. A preamble or title that carries a generator marker is refused, because the line-based tools `memory-preamble-extract` and `memforge-migrate-claim-block` do not read fences. Owner: the project |
| T15 | A8 | Tampering | A symlink, hard link or named pipe in a memory folder makes a tool write outside the folder, read an outside file, or hang | SC-14 | "On Windows, where a file cannot be opened relative to a folder handle, a folder swapped for a link or junction between the check and the open is still followed (a link already there is refused). On every platform the memory folder itself is opened by path, so replacing the whole memory folder with a link is followed. Moving, renaming and deleting a file go by path and are not covered; none of them reads or writes file content." The read-tracker hook writes `.last_used.json` with shell redirection and `mv`, outside `memforge.discovery`; it leaves a ledger that is a link or not a regular file alone, and its check and its rename go by path. `memforge-resolve` deletes a snooze relative to the snooze folder's handle on Linux and macOS; on Windows it checks and deletes by path, which does not see a junction. "On Windows, a link swapped in for a file that does not exist yet, between the check and the open, has its target created empty before the write is refused; nothing is written through it." `memory-rollup` checks its history folder by path and then lists it by path (`create` also makes a probe file under a random name in an existing history folder, exclusively, and removes only that file, before it moves anything), so a folder swapped for a link between the two is listed (names and ages only); each record is still read on the descriptor walked from the memory folder, which refuses a link. `memory-link-rewriter rename` run directly resolves a source that is a link and moves the file it names, inside the folder; `memory-rollup` refuses such a source before it calls the rewriter. Owner: the project |
| T16 | A8 | Tampering | A cloned repository commits `AGENTS.md` or `CLAUDE.md` as a link so `agents-md-gen` overwrites or copies an outside file | SC-34 | None identified for those two files. Owner: the project |
| T17 | A8, A10 | Elevation of privilege | A Python file placed in a memory folder (for example `yaml.py`) runs as code when `memforge-detect` starts its helpers | SC-26 | Other entry points run as console scripts or `python -m` chosen by the user. Owner: the user's interpreter setup |
| T18 | A12 | Information disclosure | `restricted` or `privileged` content reaches an agent, an `AGENTS.md` or an export | SC-17, SC-18, SC-19, SC-20, SC-32, SC-41 | Labels are filters, not access control. `memory-index-gen` does not filter by sensitivity. The recall hook passes no `--sensitivity-max`, so a `restricted` description can be injected. A pulled or edited recall index cannot lift a label, since the index is rebuilt from the memory files unless its fingerprint matches (SC-41). `agents-md-gen --max-sensitivity privileged` includes `privileged` descriptions; its floor is the flag. Anyone who can read the folder reads every file. Owner: the user who runs the export |
| T19 | A12 | Information disclosure | A secret written into a memory reaches the remote or `AGENTS.md` | SC-21, SC-33 | `memory-dlp-scan` is pattern-based and runs only where the user wires it (pre-commit hook, CI). The auto-commit hook and `memory-watch` do not run it. Owner: the user |
| T20 | A12 | Information disclosure | `memory-dedup` or `memory-lint` sends memory metadata or bodies to a cloud model | SC-25, SC-36 | The local-runner list decides "local" by the executable name; a runner registered in `MEMFORGE_LOCAL_DISPATCHERS` is trusted as local. With the cloud opt-in, `internal` and `public` memories are sent. Owner: the operator who names the dispatcher |
| T21 | A6 | Tampering | An untracked or locally edited waiver file turns Tier 2 BLOCKERs into warnings | SC-23 | A waiver committed in its own `memforge: waiver` commit is honored; whoever can make that commit can waive. Owner: the store's signers |
| T22 | A6, A1 | Tampering | A commit, a merge that takes the other side or writes its own result, or a move into `archive/` changes config, snoozes, supersession, group membership or resolve scope outside its `memforge:` prefix; a file named as a pattern sweeps other files into a scoped commit | SC-22, SC-05, SC-40 | Tier 2 looks back 30 days only, and only when `memory-audit` runs. A branch change older than the window is reported on the merge that brings it in, not on its own commit. With no usable `git` it is skipped with a WARN, listed under health, that does not fail `--strict`. A committed config link chain that leaves the repository is a BLOCKER on the commit that changes it; once that commit is older than the window, nothing reports it again, and the file it names is not in git and is not covered. Tier 2 reads git only, so a work-tree config and a config above the repository top are not covered, and a link above the store folder is followed before the audit starts. Owner: the store's owner |
| T23 | A11 | Repudiation | Someone edits the audit log to hide an operation | SC-35 | "`verify` detects accidental corruption and an edit that does not recompute the chain, not a rewrite or truncation by someone who can write the file." Owner: the operator, by keeping the log in the signed store or shipping it off the machine |
| T24 | A10 | Denial of service | Frontmatter of nested YAML aliases, wrong types or invalid UTF-8, or a folder a tool cannot search, hangs or stops every tool | SC-15, SC-43 | None identified beyond the per-file finding; a path the tool cannot check is reported, on every supported Python, and a folder that is there but cannot be looked at is reported, not skipped as absent. Some tools still leave out a file they cannot read without naming it (`memory-lint`, `memory-query`, `memforge-resolve`, `memory-recall`, `memory-cluster-suggest`, `memory-dedup`; `memory-frontmatter-backfill` counts them). Owner: the project |
| T25 | A3, A10 | Denial of service | A listed signer blocks later syncs on purpose | SC-04 (blocks only the accidental case) | "A listed signer can block later syncs on purpose, with a valid list of keys nobody holds or a switch to a mode receivers refuse." Owner: the store's owner |
| T26 | A3, A10 | Denial of service | A `keyless` trust-root or log outage refuses every commit | SC-02 (the mode is refused) | "`keyless` also refuses every commit during an outage of its trust roots or log." "`keyless` has not been run." Owner: the project, before release of the mode |
| T27 | A7 | Information disclosure | A tool reads a signer's private key | `memforge init-store` reads only the `.pub` half of `user.signingkey` | MemForge holds no keys. "A stolen or misused listed key" is not stopped by commit trust (spec, "What commit trust does not stop"). Owner: the signer |
| T28 | A9 | Spoofing | Someone who can push a tag publishes a release | SC-27, SC-28, SC-29 | Approval on the `pypi` environment is a repository setting; the workflow names the environment and does not check its rules. Owner: the maintainer |
| T29 | A9 | Tampering | The release tag is moved or replaced while the build and publish run, or a file attached to the GitHub Release is replaced afterwards | SC-30, SC-38 | "The build and the PyPI upload always use the checked commit, whatever the tag does; this last check runs after the upload and guards only the release page. The release page names the tag, so a tag moved after that last check is not caught by the workflow; keeping release tags from moving is a repository setting." A replaced release file fails `gh attestation verify` and no longer matches its sha256 in the release notes, but only a reader who runs the check finds out; someone who can edit the release can also edit the notes, so the check that does not rest on the release page is `gh attestation verify` with the signer workflow named, as `docs/runbooks/release.md` shows. The `publish` job does not wait for the attestation, so a failed `attest` job leaves the PyPI upload in place and stops only the GitHub Release. A PDF rebuilt elsewhere can differ in layout, since fonts and system libraries come from the runner image. Owner: the maintainer, and the reader who verifies a download |
| T30 | A9 | Tampering | A pull request edits the DCO workflow or its checker to pass itself | SC-31 | None identified for the DCO check. Owner: the maintainer |
| T31 | A3, A10 | Denial of service | A long range makes `memforge sync` slow | None | "Verification costs one `verify-commit` per commit in the range being checked." Owner: the receiver |
| T32 | A3 | Tampering | A store that lives in a subfolder of a larger repository shares one state key with other content | SC-08 | "The store must be the top level of its git repository." A store in a subfolder cannot use `sync` until it moves. Owner: the store's owner |
| T33 | A9, A8 | Information disclosure | A docs change makes the attested architecture PDF carry a file from the build machine or bytes fetched at build time | SC-39, SC-38 | The page loads no file, so a link or path in the Markdown or stylesheet reaches nothing outside the inputs; the inputs themselves are checked to be regular files, not links, by path before they are read; every entry of the diagrams folder is checked, whatever its name or case, and the filter opens a diagram only under an exact name from that checked list. `docs/pdf/build-pdf.sh`, `docs/pdf/architecture.lua` and `docs/pdf/architecture.css` are files a merged docs change can edit, and the checks live in them. The Chrome download is pinned by version, not by checksum. Owner: the maintainer, through review of `docs/` |
| T34 | A8, A5 | Information disclosure | `agents-md-gen` copies a file from outside the repository, such as the user's private instructions in the home folder, into the AGENTS.md the repository commits | SC-34 | None identified: beside the memory folders it reads only `<cwd>/CLAUDE.md` and an existing `<cwd>/AGENTS.md`. Memory descriptions at or below `--max-sensitivity` still reach the file by design (T18). Owner: the project |
| T35 | A3, A10 | Denial of service | A listed signer commits a valid signer list padded to any size, so every receiver reads it whole for each commit judged against it | SC-03, SC-44 | A list up to 1 MiB is still read for each commit judged against it. A list wrapped in a tag, or a tree with millions of entries under `.memforge/`, no longer lifts the cap or the memory `memforge sync` itself uses, though git still holds the tree object it reads in its own process. `memforge sync` reads each commit object whole in its first-parent walk, with no size bound. Owner: the project |
| T36 | A5, A12 | Tampering | A recall index that arrives with `git pull`, or is edited by hand, carries entries, `always` flags, `access` labels or a `folder` that make recall inject text, drop a `do_not_inject` memory's flag or name another folder | SC-41, SC-18 | The index is a local cache that no tool commits and is rebuilt unless its stored fingerprint of the memory files matches; a pulled copy cannot match, since a fresh checkout has its own modification times. The index also records its build time, and a memory file modified within 2 seconds of it (inclusive, either side) forces a rebuild, so a same-size edit in the same file-clock tick as the build cannot be served stale. A process that can write both the index and the memory files can compute the fingerprint, which is not secret, but it can already change the memories themselves. Owner: the user |
| T37 | A1, A8 | Tampering | A file name, name, description or quoted text holds a terminal escape sequence, so a tool's output writes the clipboard, retitles the window, erases lines or forges an output line | SC-42 | `memforge paths` writes folder names as bytes by design. Commit messages that tools write carry names as given, except the hook, which replaces control characters (SC-12). Text copied out of a terminal into another program is the user's. Owner: the project |
| T38 | A1, A6, A10 | Tampering | A folder on the way to a memory folder, or a store file, is made unreadable so a tool takes it for absent and judges, resolves or audits without it | SC-43 | `memory-recall` answers from nothing when it cannot read, since recall is fail-open-empty by spec. Some tools still leave out a single file they cannot read without naming it (T24). Owner: the project |

## Residual risks stated by the release

These are quoted from `spec/known-limitations.md`, so a reader finds them here in the same words.

- **Mechanisms not yet proven with the real tools.** "`keyless` has not been run." "`gpg` was observed in a scratch setup, not proven in CI." "Host-generated commits are unverified." "The environment passed to `gitsign` has not been run." "Environment injection through `GIT_CONFIG_COUNT` was not tested." "The first-sync pin is a statement, not a check."
- **External review.** "This is not an external audit. The project's own review does not replace independent red-teaming or a third-party penetration test, and neither has been performed."

## Out of scope

- The git host's access control, branch protection and required signing: the host and the store's owner.
- The security of signers' keys and machines: each signer and their organization.
- What an agent does with the context it loads, including prompt injection in content a trusted signer wrote: the agent's vendor and the user.
- File-system permissions, disk encryption and backups of the memory folders: the user.
- The model providers behind any dispatcher the operator names: the operator.
- The adapters' host tools (Claude Code, Cursor, Aider, Codex, Copilot Chat) and how they load files: their vendors.
- `detect-secrets`, `gpg`, `gitsign`, `ssh-keygen` and `git` themselves: their projects.
- GitHub and PyPI platform security: those platforms.
